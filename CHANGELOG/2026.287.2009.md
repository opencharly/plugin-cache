# 2026.287.2009 — feat(cache): `charly cache ingest <ref>` — the ONE registry ingest route, into the named `registry` store (charly#892)

## Summary

`charly registry cache add` (in `opencharly/charly-registry`) is a **second ingest route** for a capability the cache machinery already has a route for — and it is one that **cannot work**: an out-of-process `command:` plugin is `syscall.Exec`'d in CLI mode with the go-plugin handshake cookie stripped, so it has no broker and no `Executor`, and can never reach `verb:oci` where the go-containerregistry transport is single-homed. This PR lands the ingest where the reverse channel actually exists — the compiled-in `charly cache` route — so the duplicate client can be **deleted** and `charly-registry#7` closed (R2, producer-first).

**One surface added, on the existing route — no new verb, no new wire type.** `charly cache ingest <ref>` reuses `transferCache`'s peer-dispatch seam and the existing `spec.CacheTransferRequest`/`Reply` pair (CUE-single-sourced in `spec/schema/oci.cue`); it adds the leaf, not a route.

- **`charly cache ingest <ref> [--store registry] [--insecure] [--refresh]`** — fetches ONE remote ref through the same seam, then lands it in a named `sdk/storekit` store **keyed by that ref**: every blob content-addressed by digest (`PutBlob`, idempotent by construction), then the keyed entry **LAST** (`PutEntry`) — an ordering the API itself enforces, since `PutEntry` hard-errors unless `Payload` is already a blob in the store.
- **D-STORE-5 on the way in, both halves asserted by an unchanged blob count** (below): a tag-addressed request resolves to a digest **once**, recorded in the entry's annotations (`ai.opencharly.registry.repo`, `ai.opencharly.registry.tag`, `ai.opencharly.registry.resolved`), so a repeated tag request does **no second fetch**, and a re-run at an unchanged digest does **no second write**.
- **The store ROOT moves with the repoint, and that is part of this claim rather than a side effect.** `storekit.StoreDir` resolves under the **CACHE** root — `~/.cache/charly/registry` (`CHARLY_CACHE_DIR` the one override) — whereas `spec/cache.StoreDir`, which `push`/`pull` keep using, resolves under the **CONFIG** root (`~/.config/charly/cache/<name>`). `storekit`'s own header names the old root as D-STORE-1's deviation (`spec#233`).
- **`go.mod`**: `sdk v0.2026287.1747` + `spec v0.2026287.1529` — `storekit`'s first publication (sdk#387, merged 17:00:48Z). `github.com/opencontainers/image-spec` is promoted from indirect to direct (the OCI constant vocabulary: `index.json`, the image-index media type — never hand-spelled).

- **`charly.yml`** — this repo's FIRST `disposable: true` check bed (`check-cache-ingest`) plus its `kind:local` template, so a compiled-in plugin change can run its change-class gate (see *How tested*; the bed's completion is `plugin-cache#10`).
- **`.gitignore`** (+3) — ignores `.check/`, where that bed RETAINS its run evidence and its step log; the umbrella ignores the same path for the same reason, and without it every bed run would leave untracked files in the tree.
- **`go.sum`** — the checksum swap that follows the `go.mod` pin move above (the old `sdk`/`spec` version lines replaced; no new module added).

**What this deliberately does NOT do (measured boundaries, each with a coordination post):**

1. **The single-image arm stays in `plugin-oci`.** `runCachePull` is `remote.Index(ref)` only, so a single-image ref cannot be fetched; the team lead ruled that arm made by `oci-plugin-lead` inside its live `plugin-oci#13` (a file one session is already editing must not acquire a second writer), and I posted the requirement, the measurement and the coordination there ([comment](https://github.com/opencharly/plugin-oci/pull/13#issuecomment-6176292129)). The ingest reads whichever shape the transport writes: it distinguishes them by **measurement** (whether `index.json`'s own bytes hash to the digest the transport reported), not by a guess.
2. **No `oci-layout` marker is written from a consumer.** The `storekit` writer never creates the marker its own reader requires, so a store built through the blessed API is invisible to `NamedStores()` — a consumer writing it would implement the SDK's contract in a third home. Filed instead: **sdk#390**.
3. **`storekit` has no entry delete**, so `cache rm <ref>` cannot remove a ref and deleting blobs alone leaves a dangling descriptor (the ref still lists, reads 404). Filed: **sdk#391** — with `registry-serving-lead`'s live serving-side manifestation added, and cited here rather than duplicated.

**⚑ Two defects in the bed itself, and the first green run was GREEN FOR THE WRONG REASON.** Both were caught by reading the run's RETAINED evidence instead of its step summary:
1. `${CHARLY_BIN}` must be spelled **braced** inside a step script: the runner substitutes that spelling, and the unbraced form is left to the shell, where `set -u` makes it unbound — my first run's log contained `sh: line 16: CHARLY_BIN: unbound variable` while the step reported PASS.
2. **A step's `arms | tee "$LOG"` pipeline returns `tee`'s status, not the arms'** — so a step that did NOTHING exited 0 and satisfied its `stdout: contains:` matcher. The arms now write their own log, the step asserts each arm's marker in it, and the step's exit status is the arms'. This is the rulebook's own "a piped exit code is not the command's exit code" with a check step as the object, and it is why the evidence above is pasted **from the retained log**, not from the run's summary line.

### The two R1 anomalies this run surfaced, both RCA'd with the missed control

1. **`plugin-build@v0.2026280.647` cannot compile against `sdk v0.2026287.1747`.** Mechanism: this PR is the first plugin to require the sdk tag that carries `storekit`, so MVS raises the graph's `sdk` (`v0.2026281.2051` → `v0.2026287.1747`), and the pinned `plugin-build` still passes the pre-`NamespaceAncestors` closure into a `loaderkit` seam the newer sdk typed differently — `cannot use func(… visited map[*spec.UnifiedFile]bool) … as func(… ancestors loaderkit.NamespaceAncestors)`. Missed control: the repo's pin set was never held against the sdk it now resolves. Blast radius: **any** assembled charly build with `sdk ≥ .1747` — this wave's whole store migration, not this diff. `plugin-build v0.2026286.1121` (the pin `charly#877` already adopts) compiles against `sdk .1747` — `go build ./...` rc=0 in a probe. The live venue above therefore bumped that one pin **in the build venue only**; nothing in this diff touches pins outside `plugin-cache`.
2. **A wrong instrument made a test fail, and the instrument was mine.** The mutation run's first expectation (`2 blobs after the first ingest`) was wrong: `PutEntry` publishes the entry manifest as a blob of its own, so the honest count is 3. The code was right; the expectation was fixed.
